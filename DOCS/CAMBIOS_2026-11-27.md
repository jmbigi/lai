## 1. `llm.rs` — el cliente no hablaba el protocolo que anunciaba

**ANTES**

- `ToolChoice` tenía `#[serde(untagged)]`, así que `ToolChoice::None`,
  `Auto` y `Required` se serializaban como `null`. El servidor recibía
  `"tool_choice": null` en lugar de `"auto"`. Funcionaba por accidente con
  llama.cpp; no es el contrato de [OI].
- `Message.content` era `String` sin `#[serde(default)]`. Cuando el servidor
  devuelve `{"role":"assistant","content":null,"tool_calls":[...]}` —lo normal
  cuando el turno es solo una llamada a herramienta— **fallaba la
  deserialización de toda la respuesta**.
- `ToolCall.id` y `call_type` eran obligatorios y `function.arguments` solo se
  aceptaba como string. Varios servidores locales omiten el `id` o mandan los
  argumentos como objeto JSON.
- `reqwest::Client::new()` sigue redirecciones sin comprobar el destino: un
  endpoint local podía redirigir a uno público y saltarse la **Regla 4**.

**DESPUÉS**

- `ToolChoice` tiene `Serialize`/`Deserialize` manuales: `"none"`, `"auto"`,
  `"required"` y `{"type":"function","function":{"name":…}}`.
- `content: null` y `content` ausente se leen como cadena vacía
  (`null_to_empty_string`).
- `ToolCall.id` y `call_type` tienen `default`; `arguments` acepta string,
  objeto o `null` (`string_or_json_string`), normalizándolo siempre a string
  JSON, que es lo que consume el resto del código.
- La política de redirecciones de `reqwest` consulta `is_local_url()` en cada
  salto y aborta si el destino no es local, salvo `--allow-remote`. El flag se
  comparte con el cliente mediante un `Arc<AtomicBool>`.

Verificado con `lai auto` contra un servidor falso: los seis turnos enviaron
`"tool_choice": "auto"` (antes `null`).

Tests nuevos: `tool_choice_serializes_to_openai_strings`,
`null_message_content_deserializes_as_empty`,
`tool_call_accepts_object_arguments_and_missing_fields`.

## 2. `tools.rs` — comandos sin límite de tiempo y escrituras destructivas

**ANTES**

| Defecto | Consecuencia |
|---|---|
| `run_command`/`run_python` usaban `Command::output()` | Un test colgado bloquea el agente para siempre. El esquema anunciaba `timeout` y se ignoraba. |
| `write_file` con `content` ausente usaba `""` | Un modelo que olvida el campo **vacía el archivo** y la llamada devuelve éxito. |
| `apply_patch` con `path` que no es directorio caía a `"."` | Aplicaba el parche en el directorio equivocado sin avisar. |
| El fallback a `patch` solo ocurría con «not a git repository» | Si `git` no está instalado, el error era «could not run git» y nunca se intentaba `patch`. |
| `repo_map` cortaba en `trimmed[4..]` | `async fn foo` se mostraba como `fn c fn foo`; `pub fn`/`pub struct`/`enum`/`trait` no se detectaban; recorría `target/` y `node_modules/`. |
| `run_python` guardaba la ruta del `NamedTempFile` y escribía después | Carrera entre el borrado del temporal y la escritura; en Windows el handle abierto puede impedir que Python lea el archivo. |
| Los comandos que fallaban no mostraban el código de salida | El modelo no podía distinguir «sin salida» de «falló». |

**DESPUÉS**

- `run_with_timeout()` lee stdout/stderr en hilos y hace `try_wait()` en bucle.
  Al vencer el plazo mata **el grupo de procesos** (`process_group(0)` +
  `kill(-pid, SIGKILL)` en Unix), porque `sh -c "sleep 5"` deja un nieto vivo
  que mantiene los pipes abiertos. Límites: `run_command` 300 s (máx. 3600),
  `run_python` 60 s (máx. 600).
- `write_file` exige `content`; si falta, devuelve error sin tocar el archivo.
- `apply_patch` exige que `path` sea un directorio existente.
- El fallback a `patch --dry-run` se intenta también cuando `git` no está
  disponible.
- `symbols_in_source()` reconoce `pub fn`, `async fn`, `pub async fn`,
  `struct`/`pub struct`, `enum`, `trait`, `def`, `async def`, `class`, y el
  recorrido usa `is_skipped_dir()` como `grep`/`find_files`.
- `run_python` usa `into_temp_path()` (cierra el handle antes de ejecutar y
  borra al salir del ámbito) y escribe con `fs::write`.
- stdout/stderr de comandos y Python llevan `EXIT CODE: n` cuando el proceso
  falla.

Tests nuevos: `write_file_requires_content_instead_of_truncating`,
`apply_patch_rejects_a_file_instead_of_silently_using_cwd`,
`repo_map_extracts_rust_visibility_and_async_symbols`,
`run_command_requires_a_command`, `run_command_honours_the_timeout`,
`run_python_requires_code`.

## 3. `policy.rs` — la frontera del workspace se podía cruzar

**ANTES**

- `is_within_workspace()` usaba `canonicalize()` y, si fallaba (archivo que aún
  no existe), comparaba la ruta **sin colapsar `..`**. `../fuera.txt` empezaba
  por el prefijo del workspace y se aceptaba.
- `is_protected()` comparaba subcadenas: `notsrc/main.rs` y `Cargo.toml.bak`
  se trataban como protegidos.
- La lista de protegidos era `src/`, `.git/`, `Cargo.toml`, `Cargo.lock` para
  **cualquier** workspace. En un proyecto de usuario, `src/` es exactamente lo
  que el asistente debe poder editar: la herramienta quedaba inutilizable.

**DESPUÉS**

- `resolve_for_policy()` canonicaliza la ruta, o su directorio padre, o aplica
  un colapso léxico de `.`/`..` si nada existe.
- `is_protected()` compara **componentes** de la ruta relativa.
- Siempre protegidos: `.git`, `.env`, `.ssh`, `.netrc`, `.npmrc`, `.pypirc`,
  `id_rsa`, `id_ed25519`.
- `src/`, `Cargo.toml` y `Cargo.lock` solo se protegen si el workspace es el
  propio repositorio de lai (`is_lai_workspace()` lee `Cargo.toml` y busca
  `name = "lai"`, en la raíz o en `lai_rust/`).
- `commands.rs::cmd_auto` enruta `write_file` y `apply_patch` por
  `ToolRegistry::call_tool()`, que consulta el `PolicyEngine`. Antes se llamaba
  la función directamente y la política nunca se aplicaba en `auto`. Los
  comandos de shell se dejan sin allowlist a propósito: la lista actual
  (`cargo`, `git`, `ls`…) bloquearía `python`, `cd` o `sed`, que el agente
  necesita, y no forma parte de este arreglo.

Tests nuevos (en `tests/core.rs`): `…protected_paths_use_components_not_substrings`,
`…blocks_parent_traversal_for_new_files`,
`…allows_src_in_a_user_workspace`.

Comprobado con el binario:

```
write_file .git/config      → PolicyEngine blocked: Protected path
write_file ok.txt           → Written to ok.txt
write_file ../escape.txt    → PolicyEngine blocked: Outside workspace
```

## 4. `mcp_server.rs` — `resources/*` no funcionaba en Linux nativo

**ANTES**

- `resources/list` anunciaba `file:///workspace/AGENTS.md` y `README.md`
  siempre, existieran o no, apuntando a `/workspace`, una ruta que solo existe
  dentro de los contenedores de SWE-bench.
- `resources/read` hacía `Path::new("/workspace").join(path)` y comprobaba
  `starts_with("/workspace")` sobre la ruta **sin canonicalizar**, así que
  `file:///workspace/../../etc/passwd` pasaba la comprobación.

**DESPUÉS**

- `McpServer` guarda `workspace_root` (directorio actual, copiado también en
  `Clone`).
- `resolve_workspace_path()` acepta el formato histórico
  `file:///workspace/…`, `file:///ruta/absoluta` y rutas relativas; canonicaliza
  workspace y destino y exige que el destino esté dentro del workspace y sea un
  archivo.
- `resources/list` emite URIs `file://` absolutas y solo de archivos que
  existen.

Tests nuevos: `resolves_legacy_and_absolute_file_uris`,
`rejects_paths_outside_the_workspace`,
`resources_read_does_not_escape_the_workspace`.

Comprobado por stdio con el binario de release:

```
tools/list            → 13 herramientas
resources/list        → file:///home/kubuntu/lai/AGENTS.md, …/README.md
resources/read ../…   → Access denied: path outside workspace
```

## 5. `services.rs` — los binarios del PATH se daban por ausentes

**ANTES:** `start_service()` comprobaba `Path::new(script).exists()`. Los
valores por defecto (`llama-server`, `gateway`, `ollama`) no son rutas
relativas al directorio actual, así que aunque estuvieran en el `PATH` se
informaba «No executable found».

**DESPUÉS:** `resolve_executable()` usa `which::which()` para nombres sin
separadores y `is_file()` para rutas. Dos tests.

## 6. `commands.rs` — la normalización borraba los argumentos que la guarda pedía

**ANTES**

- `normalize_tool_arguments("write_file")` reconstruía el mapa con solo
  `path` y `content`. Cuando `write_file` rechazaba una escritura y pedía
  reintentar con `"allow_shrink": true`, el normalizador borraba la bandera y
  el reintento **volvía a fallar exactamente igual** (bucle).
- `run_command` y `run_python` descartaban `timeout`.
- La heurística de «esto es un comando de shell» no incluía `python3`, el
  nombre habitual del intérprete en Linux.

**DESPUÉS:** los normalizadores conservan el mapa original y solo corrigen los
campos conocidos; `looks_like_shell_command()` incluye `python3`. Tres tests
nuevos y comprobación de punta a punta (ver §8).

## 10. Lo que NO se ha probado

- **El modelo real.** No hay llama.cpp ni Ollama levantados en esta máquina
  (`lai status`: los tres servicios parados). Todo el bucle se validó con un
  servidor falso que imita el protocolo. Un piloto SWE-bench con
  `qwen2.5-coder:7b` sigue pendiente y es lo único que puede dar una cifra de
  resolución.
- **Windows.** Los cambios usan `#[cfg(unix)]` para el grupo de procesos y
  `#[cfg(target_os = "windows")]` para las comparaciones de rutas; solo se
  compiló y ejecutó en Linux.
- **La allowlist de comandos** no se aplica todavía en `auto` (ver §3). Es una
  decisión de producto pendiente: ampliarla o hacerla configurable.
