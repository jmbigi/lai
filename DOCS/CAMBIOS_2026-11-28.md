## 1. `ruff check .` volvía a fallar

**Archivo afectado:** `swebench/run_eval.py`.

**ANTES:** el último commit añadió

```python
any(name and name.split(":")[0] == model.split(":")[0] for name in names)
```

y `ruff` lo rechazaba con `PLC0207` («String is split more times than
necessary»). La suite Python estaba en verde, pero el lint del producto no.

**DESPUÉS:** `split(":", maxsplit=1)` y el `any(...)` partido en varias líneas.
También se añadió la línea en blanco que faltaba entre `uses_host_network` y
`container_base_url_warning`.

**Verificación:** `ruff check .` → `All checks passed!` sin el aviso de
configuración obsoleto (ver §5).

## 2. `lai tui` sin TTY y restauración de la terminal

**Archivo afectado:** `lai_rust/src/tui.rs`.

**ANTES**

- Sin TTY, `enable_raw_mode()` devolvía
  `No such device or address (os error 6)`. El mensaje no explicaba qué hacer.
- Si `run_event_loop()` fallaba, `run()` propagaba el error con `?` **antes** de
  llamar a `restore_terminal()`: la terminal quedaba en modo raw y con la
  pantalla alternativa activa.
- Si `EnterAlternateScreen` fallaba después de `enable_raw_mode()`, el modo raw
  tampoco se deshacía.

**DESPUÉS**

- `ensure_interactive(stdin_is_tty, stdout_is_tty)` devuelve un error accionable:
  «`lai tui` necesita una terminal interactiva (TTY)… para uso no interactivo
  están `lai chat`, `lai auto` y `lai mcp`».
- `run()` restaura la terminal **siempre**, también cuando el bucle falla.
- `setup_terminal()` deshace el modo raw si falla la entrada en pantalla
  alternativa o la creación del `Terminal`.

**Verificación**

| Caso | Comando | Resultado |
|---|---|---|
| Sin TTY | `lai tui > out 2> err` | código 1, mensaje accionable en `err` |
| Con PTY | `script -qec "lai tui" /dev/null` + Ctrl+C | código 0; el log termina con `[?1049l` y `[?25h` (sale de pantalla alternativa y muestra el cursor) |

Dos tests nuevos: `rejects_a_piped_stdin_or_stdout_with_an_actionable_message`
y `accepts_a_real_terminal`.

## 3. Guarda de manifiestos (pendiente del benchmark)

**Archivo afectado:** `lai_rust/src/tools.rs`.

**ANTES:** `write_file` podía sustituir `Cargo.toml`, `package.json`,
`pyproject.toml`, etc. por contenido inventado. Ocurrió en el benchmark del
2026-11-26: `qwen2.5-coder:3b` reemplazó `Cargo.toml` y rompió el proyecto. No
había ninguna guarda, solo la de reducción de tamaño (40+ líneas), que no cubre
manifiestos cortos.

**DESPUÉS**

- `is_manifest_file()` reconoce `Cargo.toml`/`Cargo.lock`, `package.json` y
  *lockfiles* de npm/yarn/pnpm, `pyproject.toml`, `setup.py`, `setup.cfg`,
  `requirements.txt`, `go.mod`/`go.sum`, `Gemfile`/`Gemfile.lock`,
  `composer.json`/`composer.lock`, `pom.xml` y `build.gradle(.kts)`.
- `write_file` rechaza reemplazar un manifiesto existente con contenido distinto
  salvo `"allow_manifest_overwrite": true`. El error recomienda `edit` para un
  cambio puntual (por ejemplo, añadir una dependencia).
- `edit` rechaza el caso equivalente: `old_string` que abarca el manifiesto
  completo. Un fragmento parcial sigue permitido.
- Crear un manifiesto nuevo no se bloquea (no hay nada que destruir).
- Los esquemas de ambas herramientas documentan la bandera nueva.

**Verificación de punta a punta** con un servidor [OI] falso y `lai auto`:

```
Iteration 1 → write_file Cargo.toml          ✗ Error: es un manifiesto… usa `edit`
Iteration 2 → edit de un fragmento parcial    ✓ Done
Iteration 3 → edit de [dependencies]          ✓ Done
Iteration 4 → respuesta final                 ✅
```

Cinco tests nuevos: rechazo y permiso en `write_file`, creación de manifiesto
nuevo, rechazo de `edit` sobre el archivo completo y permiso para un `edit`
parcial.

> **Límite declarado:** `apply_patch` y el perfil `bash` no pasan por esta
> guarda. Un diff que reemplace todas las líneas de un manifiesto, o un
> `cat > Cargo.toml` dentro del perfil bash, seguirían siendo posibles; no se
> observaron en las corridas y bloquearlos exigiría interpretar el diff o
> inspeccionar comandos arbitrarios.

## 4. Los enunciados del benchmark declaran las restricciones

**Archivos afectados:** `run_benchmark.sh`, `run_competition.sh`,
`run_stress.sh`, `swebench/run_eval.py`.

**ANTES:** el segundo hallazgo del benchmark del 2026-11-26 quedaba abierto: el
agente cambió `add(i32, i32) -> i32` por `add(&str, &str) -> Result<…>` y rompió
un test preexistente. Los enunciados no decían que las APIs públicas existentes
debían conservarse, así que parte del fallo era del diseño de la tarea.

**DESPUÉS**

- `run_benchmark.sh` y `run_competition.sh` anteponen a cada tarea:
  «No elimines ni reemplaces APIs públicas existentes y no sustituyas
  Cargo.toml; cambia solo lo necesario…».
- `run_stress.sh` antepone la misma regla en inglés.
- `swebench/run_eval.py::build_task` añade: «Do not remove or replace existing
  public APIs; keep their signatures unless the issue explicitly requires a
  change».

**Verificación:** `bash -n` en los tres scripts y
`swebench/test_run_eval.py` → 43/43.
